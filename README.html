Báo Cáo: Git Reset vs Git Revert

Khôi phục trạng thái cục bộ và đảo ngược commit an toàn trên nhánh chung

📚 Môn: DevOps / Git Version Control
👤 Học viên: Longle183
🛠️ Công nghệ: HTML5 & Vanilla JavaScript
🔗 GitHub Repo

1. Mục tiêu bài tập

Thực hành hai kỹ thuật xử lý commit lỗi trong Git:

  • Trường hợp 1 (Cục bộ) – Dùng git reset --mixed để lùi HEAD về commit trước, giữ mã nguồn ở Working Directory dạng Unstaged để viết lại.
  • Trường hợp 2 (Công cộng) – Dùng git revert để tạo một commit đối lập đảo ngược thay đổi, an toàn khi đẩy lên nhánh chung với nhóm.
📋
2. Bối cảnh dự án

Dự án là ứng dụng quản lý công việc TaskFlow (HTML + Vanilla JS) với các tính năng: thêm/xóa/lọc/tìm kiếm/sắp xếp nhiệm vụ theo mức ưu tiên.

Trong quá trình phát triển, lập trình viên tạo ra các commit chứa lỗi và cần thực hành hai kỹ thuật sửa lỗi khác nhau tùy theo ngữ cảnh.

↩️
3. Trường hợp 1: Git Reset (Sửa lỗi cục bộ)
⚠️ Tình huống: Vừa commit một thuật toán sắp xếp có bug nghiêm trọng (undefinedVariable) nhưng chưa đẩy lên remote. Cần lùi HEAD lại và viết lại code.
1
Kiểm tra trạng thái trước khi reset
# Xem lịch sử commit git log --oneline -n 5 d0bafa0 feat: add experimental task sorting algorithm (buggy) a07ec09 feat: add filter and search functionality 68eff2a feat: initialize task management web app with HTML and JS
2
Thực hiện git reset --mixed HEAD~1
# Reset lùi 1 commit, giữ thay đổi ở Working Directory (không mất code) git reset HEAD~1 Unstaged changes after reset: M app.js

Lệnh git reset mặc định dùng chế độ --mixed. HEAD lùi về commit trước, các thay đổi vẫn còn trong file nhưng bị unstaged — không mất code.

3
Kiểm tra trạng thái sau reset
git status On branch main Changes not staged for commit: (use "git add <file>..." to update what will be committed) modified: app.js no changes added to commit
✅ Kết quả mong đợi đạt được: HEAD lùi lại, app.js nằm trong Working Directory dạng Modified (Unstaged). Mã nguồn được giữ nguyên để viết lại.
4
Viết lại code đúng và commit lại
# Sửa lỗi trong app.js (thay undefinedVariable bằng logic đúng) # function sortTasks() { tasks.sort((a,b) => b.id - a.id); ... } git add app.js git commit -m "fix: rewrite sortTasks with correct logic after reset" [main 2bab311] fix: rewrite sortTasks with correct logic after reset 1 file changed, 16 insertions(+), 3 deletions(-)
🔄
4. Trường hợp 2: Git Revert (Sửa lỗi công cộng)
ℹ️ Tình huống: Commit chứa lỗi nghiêm trọng (deleteTask xóa toàn bộ danh sách thay vì 1 task) đã được push lên remote. Các thành viên nhóm đã pull về. Không thể dùng reset vì sẽ phá lịch sử chung.
1
Xác nhận commit lỗi đã tồn tại trên remote
git log --oneline -n 4 aad26b3 feat: update delete function (critical bug - deletes all tasks) 2bab311 fix: rewrite sortTasks with correct logic after reset a07ec09 feat: add filter and search functionality 68eff2a feat: initialize task management web app with HTML and JS
2
Thực hiện git revert để tạo commit đối lập
# Đảo ngược commit cuối cùng, --no-edit dùng message mặc định git revert HEAD --no-edit [main 7cd81dc] Revert "feat: update delete function (critical bug - deletes all tasks)" Date: Tue Oct 6 00:03:29 2026 +0700 1 file changed, 5 insertions(+), 4 deletions(-)

Git tự động tạo một commit mới đảo ngược mọi thay đổi của commit bị lỗi. Lịch sử không bị xóa — commit cũ vẫn còn nhưng được vô hiệu hóa bởi commit Revert.

3
Đẩy commit Revert lên remote an toàn
git push origin main To https://github.com/Longle183/Session04_IT209_Ex5 aad26b3..7cd81dc main -> main

✅ Kết quả mong đợi đạt được: Commit đầu tiên có tiêu đề bắt đầu bằng Revert "..." xuất hiện trên đầu nhánh. Lịch sử đầy đủ, an toàn cho làm việc nhóm.

5. So sánh Git Reset vs Git Revert
Tiêu chí git reset git revert
Cơ chế hoạt động Di chuyển con trỏ HEAD về commit cũ hơn Tạo commit mới đảo ngược thay đổi
Lịch sử commit Bị xóa/thay đổi Được bảo toàn
Tác động lên remote Không nên dùng nếu đã push (cần force push) An toàn, push bình thường với git push
Phù hợp khi nào Commit chưa push, đang làm việc cá nhân Commit đã push, đang làm việc nhóm
Rủi ro với nhóm Cao – phá lịch sử chung Thấp – an toàn cho nhóm
Chế độ giữ file --soft (staged), --mixed (unstaged), --hard (xóa) Luôn giữ nguyên, tạo commit nghịch đảo
Khả năng rollback Cần dùng git reflog để phục hồi Dễ dàng — chỉ cần revert commit Revert
👥
6. Cá nhân vs Làm việc nhóm: Khi nào dùng gì?

🧑‍💻 Làm việc cá nhân (local)

Dùng git reset khi commit sai chưa push lên remote:

  • Nhanh chóng, không tạo thêm commit thừa
  • Có thể chọn mức độ giữ file: soft / mixed / hard
  • Hoàn toàn an toàn vì chỉ ảnh hưởng máy bản thân
  • git reset HEAD~1 (mixed – giữ code unstaged)
  • git reset --soft HEAD~1 (giữ code staged)

👥 Làm việc nhóm (shared branch)

Dùng git revert khi commit lỗi đã push lên nhánh chung:

  • Không phá lịch sử, đồng đội không bị ảnh hưởng
  • Tạo commit rõ ràng ghi lại lý do đảo ngược
  • Có thể push lên remote ngay bằng git push
  • Trace được: ai revert khi nào, vì sao
  • git revert HEAD hoặc git revert <hash>
⚠️ Lưu ý quan trọng: Tuyệt đối không dùng git reset --hard hoặc git push --force trên nhánh chung (main/master) vì sẽ xóa lịch sử của mọi thành viên, gây mất code và xung đột nghiêm trọng.
✅
7. Kết quả kiểm tra
✅ Trường hợp 1: Sau git reset HEAD~1, con trỏ HEAD lùi lại, app.js nằm trong Working Directory dạng Modified (Unstaged). Không mất code.
✅ Trường hợp 2: Commit 7cd81dc có tiêu đề "Revert "feat: update delete function (critical bug - deletes all tasks)"" xuất hiện đầu nhánh. Lịch sử đầy đủ, đã push lên remote thành công.
